End-to-end BI solution for a fictional insurance company: data from **three source systems** (two CSV exports and a separate PostgreSQL database) is extracted, validated, cleaned and loaded into a **PostgreSQL star-schema warehouse**, then reported in **Power BI** (loss ratio, claim frequency, claim severity, revenue, payouts).

The focus is on what makes BI numbers trustworthy: layered architecture, explicit data-quality rules, idempotent loads, full audit trail and automated tests.

> Portfolio project built to practise BI/ETL development. All data is synthetic and generated by `scripts/generate_source_data.py`.

## What it does

```
CRM export (CSV)   ─┐
Claims export (CSV)─┼─► STAGING ─► VALIDATION ─► WAREHOUSE (star schema) ─► REPORTING VIEWS ─► Power BI
Policy Admin DB   ──┘   (raw)      (rules,       (dims + facts, PK/FK,        (rpt schema)
(PostgreSQL)                        dedup,         constraints, indexes)
                                    lookups)
                              └──────► AUDIT: runs, step row counts, rejected rows + reason, quality gate
```

- **Extract** from 2 CSV files and from a second PostgreSQL database (`src_policy_admin`) into staging.
- **Validate** with 20+ documented rules: orphan references, invalid dates in 3 formats, negative/missing amounts, paid > claimed, claims outside policy coverage, duplicates.
- **Load** dimensions and facts with idempotent upserts that update only changed rows.
- **Audit** every run: rows read / inserted / updated / unchanged / duplicate / rejected, duration, and every rejected record with its reason and raw values.
- **Quality gate**: reconciliation and threshold tests fail the run before bad data reaches the dashboard.
- **Report**: reporting views + DAX measures for a 3-page Power BI dashboard (Executive, Claims, Data Quality).

Top rejection reasons (claims): invalid amount (4), paid exceeds claimed (3), orphan policy (3), claim outside coverage (2), invalid date (1). Full run takes about 1.5 s locally.

`tests/run_tests.sh` → **12 passed**: SQL unit tests, idempotent re-run (0 inserts, 0 updates), change detection (exactly 1 row updated), failure handling (missing file → run marked `FAILED`, warehouse untouched).

## Run it

**Prerequisites:** PostgreSQL 14+ (or Docker), `psql` on PATH, Python 3, Bash (Linux/macOS, or Git Bash/WSL on Windows).

```bash
cp .env.example .env              # set PGPASSWORD (and host/port if needed)
docker compose up -d              # optional: local PostgreSQL in Docker
python scripts/generate_source_data.py
./scripts/setup_databases.sh      # creates src_policy_admin + insurance_dw
./etl/run_pipeline.sh             # runs the pipeline and prints the run report
./tests/run_tests.sh              # unit + integration tests
```

Useful queries after a run:

```sql
SELECT * FROM rpt.v_etl_run_summary ORDER BY run_id DESC;           -- run history
SELECT * FROM rpt.v_dq_issue_summary WHERE run_id = 1;                -- issues by rule
SELECT record_key, rule_code, details, raw_record
FROM etl.data_quality_issue WHERE severity = 'ERROR';                -- why rows were rejected
SELECT * FROM rpt.v_kpi_product_year ORDER BY loss_ratio DESC;       -- KPIs by product
```

Power BI: follow [`powerbi/POWER_BI_BUILD_GUIDE.md`](powerbi/POWER_BI_BUILD_GUIDE.md); it includes the SQL totals the dashboard must match.

## Key design decisions

| Decision | Why | Alternative |
|---|---|---|
| Staging stores CSV values as `TEXT` | Extraction never fails on bad data; raw values are kept for auditing | Typed staging: simpler, but one bad value aborts the whole file |
| Business rules in validation **views** | One place for rules; rejects can be previewed with `SELECT` before loading | Rules inside Talend `tMap`: better when source and target are different engines |
| Transformations run inside PostgreSQL (ELT style) | Data is already in the target DB; set-based SQL is fast and testable | In-ETL-tool transformation |
| Surrogate keys + unique business keys | Warehouse independent of source key formats; enables SCD later | Natural keys: simpler, but break when sources change keys |
| Upsert with `IS DISTINCT FROM` | Idempotent; re-runs are safe and report 0 changes | Truncate & reload the warehouse: simpler, loses history, dashboard empty during load |
| Blocking vs non-blocking rules | A customer without birth date is still valid; a claim without amount is not | Reject everything imperfect: loses too much data |

Full details: [`docs/architecture.md`](docs/architecture.md) · [`docs/technical_specification.md`](docs/technical_specification.md) (requirements, rule catalogue, security, performance, known limitations).

## What I learned

- Designing a warehouse around **grain** first: one row per claim, one row per premium payment.
- Making an ETL **idempotent** and proving it with a test instead of assuming it.
- Treating data quality as a first-class output: every rejected row has a reason and its original values.
- Debugging real pipeline issues, e.g. a Bash `ERR` trap that did not fire inside functions (fixed with `set -E`) which left failed runs in `RUNNING` state.
- Validating DAX measures against independently computed SQL totals.

## Known limitations & next steps

Full extract each run, SCD Type 1 only, cash-basis loss ratio, per-step commits. Each is explained with its trade-off in the [specification](docs/technical_specification.md#9-known-limitations-documented-on-purpose). Incremental loads, retries and SCD are covered in the companion project *Multi-Source ETL & Data Quality Pipeline*.
